リアルタイム解析で“忙しい接頭区間（busy‑prefix）”を見つけるコツを、背景→アイデア→実装の順でサクッと共有します。

---

# なにが問題？

EDF/LLF などの可否判定で使う **busy window / busy prefix** 探索は、素朴にやると候補時刻が爆発しがちです。特に「無限時間」を有限チェックへ落とす橋渡し（no‑carry‑in、backlog‑free 証明）で、**どこをチェックすれば十分か**を決めるのがボトルネックになります。

# 2つの実装指向ヒューリスティクス

**A) 候補削減（reduced candidates）**
各分析窓 `window=[t0,t1]` で調べるべき時刻を、

* 窓の端点 `{t0, t1}`
* 各タスクの **直近 R 回のリリース**（R は小、例 ≤2）
* 線形緩和や LP による **不要点の刈り込み（Bini 風の demand/pruning）**
  に**限定**します。これで候補サイズは高々 `O(n·R)`、生成は `O((n·R) log(n·R))`。

**B) 正準タイブレーク（canonical tie‑breaking）**
同時刻に同優先度が並んだら、**決め打ちの規則**で事前に整列：

* まず「残り実行時間が大きいジョブ」を優先
* それでも同じなら「タスクIDが小さい方」を優先
  こうすると**スケジュール接頭列が一意（正準）**になり、探索空間が実質 “1 通り” に潰れます。検査器はその接頭列を**決定的に再生**でき、carry‑in の有無チェックが **線形時間**で済みます。

# コンパクト擬似コード

```pseudo
cands = {window.t0, window.t1}
for each task_i:
  cands ∪= last_R_releases(task_i, window)
cands ∪= lp_pruned_instants(window)  // 任意: LP/DBFベースの刈り込み

for t in sort(cands):
  if demand(t, window) > window.len:
    emit_candidate(t, contributors_with_canonical_prefix)
```

* 候補生成: `≈ O((n·R) log(n·R))`
* 各候補の妥当性検査: `≈ O(m)`（`m` はその候補で関わるジョブ数）
* `emit_candidate` には**極小の正準接頭列**（ジョブ選択列）と、**ジョブ別需要寄与**を添付 → 検査器が**決定的リプレイ**して backlog‑free / no‑carry‑in を線形で確かめられる。

# どこが“効く”のか（直感）

* 候補削減 A: EDF の需要反例は端点や**直前リリース**付近に偏ることが多い。R を小さくしても実害が出にくい。
* 正準化 B: “同点の分岐”が爆発の主因。**一意にするだけで**探索木が鎮火して、メモリと時間が激減。

# Awkernel / RocqSched への落とし込みヒント

* **Haskell 生成 + Rocq 検査**の分業に合う：

  * Haskell で `cands` と正準接頭列を量産
  * Rocq は「接頭列がルール B を満たす」「`dbf ≤ t` ⇒ 期限違反なし」の**小さなチェック**だけを信頼核で証明
* LLF でも有効：残り実行時間をキーに入れる B の規則は LLF と相性が良い。
* Coq 側では “正準接頭列を再生したら、この不等式群が必ず成り立つ” という**橋渡し補題**（busy‑window/DBF ブリッジ）を作るときに、決定性が効く。

* 候補を **端点 + 直近 R リリース +（任意で）LP 刈り込み**に絞る。
* **正準タイブレーク**でスケジュール接頭列を一意化。
* これだけで busy‑prefix 探索が現実的になり、**O((n·R) log(n·R) + m)** 近辺のコストで回る。
